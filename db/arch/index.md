# 数据库架构设计
[[toc]]

数据库架构设计关注数据如何组织、隔离、扩展和恢复。它不只涉及表结构，还包括租户边界、读写路径、部署方式、备份策略以及故障影响范围。

## 数据库架构需要考虑什么

设计数据库架构时，通常需要先回答以下问题：

- 数据由哪些业务实体组成，实体之间有什么关系？
- 不同租户或用户之间需要达到什么级别的数据隔离？
- 数据访问主要是查询、写入、批量处理，还是混合负载？
- 数据量和并发量如何增长，是否需要分片、读写分离或多副本？
- 发生节点故障、误操作或数据损坏时，如何备份和恢复？
- 哪些约束由数据库保证，哪些规则由应用层或异步任务补偿？

数据库架构没有脱离业务约束的通用最优解。相同的数据模型，在不同的数据量、一致性要求和运维能力下，可能需要完全不同的部署方式。

## 数据隔离

多租户系统常见的数据隔离方式包括：

- 每个租户独立数据库。
- 共享数据库、独立 Schema。
- 共享数据库、共享 Schema，通过租户 ID 区分数据。
- 根据租户等级或数据敏感程度采用混合模式。

不同方案分别在隔离强度、资源利用率、维护成本、扩展难度和故障影响范围之间做取舍。具体方案见[多租户数据存储](./multi-tenant.md)。

## 数据库架构与应用架构

数据库架构不是单独存在的。应用的读写模式会影响表结构和索引设计，事务边界会影响数据拆分方式，缓存和消息系统会影响一致性与恢复流程。

例如：

- 读多写少的热点数据可以使用缓存减轻数据库压力，但必须设计失效和重建机制。
- 写入量很大的业务可能需要按时间、租户或业务键分区，避免单表持续膨胀。
- 跨服务事务难以长期维持时，需要通过事件、幂等和补偿机制协调数据状态。
- 读写分离可以扩展读取能力，但副本延迟会影响读到的数据版本。

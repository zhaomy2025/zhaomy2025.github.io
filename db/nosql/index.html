NoSQL 是什么

NoSQL 通常指一组不以传统关系表和 SQL 为唯一中心的数据管理系统。这个名称常被解释为 “Not Only SQL”，重点不是拒绝 SQL，而是允许数据库根据数据形态、访问模式和扩展方式选择不同的数据模型。

关系型数据库仍然适合大量业务系统。NoSQL 解决的是另一类问题：数据结构变化快、数据规模或访问量需要横向扩展、访问模式比较明确，或者业务对象天然不适合拆成许多关系表。

为什么需要 NoSQL

互联网应用发展后，数据库面对的不只是单机上的结构化数据和事务查询，还包括：

  • 数据量持续增长，单机存储和计算能力成为瓶颈。
  • 访问量存在明显热点，需要低延迟地处理大量读写。
  • 数据结构不断变化，要求减少固定表结构带来的迁移成本。
  • 数据需要跨多个节点分布，系统必须在网络分区和节点故障时继续提供服务。
  • 某些数据之间的关系、文档结构或时间序列特征，比二维表更重要。

NoSQL 并不是“关系型数据库的升级版”，而是针对不同约束做出的取舍。引入 NoSQL 前，仍应先明确数据的访问路径、一致性要求、故障处理方式和运维能力。

常见数据模型

模型数据组织方式适合场景代表系统
键值通过 key 访问一个值或数据结构缓存、会话、计数、限流Redis
文档以 JSON 类文档保存一条记录结构变化较快的业务对象、聚合查询MongoDB
宽列按行键和列族组织大规模数据海量数据、按主键范围访问、分布式写入Cassandra、HBase
图以节点和边表示实体及关系路径查询、关系网络、推荐和风控Neo4j

一个系统可能同时使用多种模型。例如，关系型数据库保存核心交易事实，Redis 缓存热点数据，Elasticsearch 提供搜索能力。这里的关键不是把同一份数据随意复制到多个系统，而是明确哪个系统是事实来源，以及副本如何更新和重建。

NoSQL 与关系型数据库的差异

对比项关系型数据库NoSQL 系统
数据模型表、行、列和关系键值、文档、宽列、图或搜索索引
查询方式SQL 适合表达复杂组合查询通常围绕特定 key、文档、分区键或索引访问
Schema通常先定义表结构和约束部分系统允许记录结构更灵活，但仍需管理数据契约
扩展方式传统上以纵向扩展为主，也支持分片和集群很多系统从设计上强调分布式和横向扩展
事务通常提供成熟的多行事务和约束能力因系统而异，常见做法是缩小事务范围或调整数据模型
一致性常以强一致事务为基础从强一致到最终一致都有，必须看具体系统和配置

这张表只能说明常见倾向，不能替代具体产品的文档。现代关系型数据库也支持 JSON、分区、复制和分布式部署，现代 NoSQL 数据库也可能提供事务和复杂查询；选型应基于实际能力，而不是数据库名称。

分布式取舍

分布式 NoSQL 系统经常需要在数据一致性、可用性和分区容错之间做工程取舍。网络分区不是可以通过配置消失的故障：当节点之间无法通信时，系统必须决定是拒绝一部分请求以保护一致性，还是继续服务并接受数据暂时不一致。

因此，CAP 不是“任意三项只能选两项”的产品标签，也不是所有正常运行场景下的简单二选一。它描述的是发生网络分区时，系统对一致性和可用性的取舍。实际系统还要继续观察副本延迟、读写级别、故障转移、冲突解决和恢复过程。

常见的一致性策略包括：

  • 强一致读取：读取结果必须满足更严格的最新数据要求，通常会牺牲部分可用性或增加延迟。
  • 会话一致：同一个会话中，用户不会读到比自己刚写入的数据更旧的结果。
  • 最终一致：写入经过复制后，副本最终收敛；短时间内不同节点可能返回不同结果。
  • 应用层补偿：允许暂时不一致，但通过重试、幂等、消息补偿或对账修复最终状态。

什么时候适合使用 NoSQL

NoSQL 通常更适合以下情况：

  • 访问模式清晰，可以围绕 key、文档 ID、分区键或搜索条件设计数据模型。
  • 数据规模、并发量或可用性要求使横向扩展成为主要目标。
  • 数据结构变化较频繁，或者对象聚合比跨表连接更符合业务读取方式。
  • 业务能够接受特定范围内的最终一致，或已经设计好补偿机制。
  • 团队具备对应系统的备份、监控、容量规划和故障恢复能力。

什么时候不应优先使用 NoSQL

以下情况通常应先考虑关系型数据库，或至少让关系型数据库保存事实数据：

  • 业务依赖多表约束、复杂关联查询和严格的多行事务。
  • 数据之间的一致性规则比横向扩展更重要，且无法通过补偿解决。
  • 团队没有能力维护分片、复制、备份、升级和故障演练。
  • 只是因为“数据量可能变大”就提前引入 NoSQL，却没有明确的访问模式和容量数据。

小结

NoSQL 的核心不是“不用 SQL”，而是根据数据模型和访问模式选择不同的存储系统。先确定数据如何被读写、需要什么一致性和故障行为，再比较具体产品；不要先选数据库，再试图让业务迁就它。
